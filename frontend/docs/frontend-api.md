# How this app talks to the API

The browser never calls the chat API. It calls this app's own `/api/v1/*` routes
(the BFF, "backend for frontend"), which forward an allowlisted set of requests to
the API with the user's session attached.

```
browser ──same origin──▶ Next.js /api/v1/*  ──server to server──▶ chat API (API_BASE_URL)
          httpOnly cookie                      Authorization: Bearer <session token>
```

## The contract is the backend's

The API contract is generated by the backend, in this repository:

| Document (repository root) | What it is |
|---|---|
| `docs/api-contract.md` | Endpoints, payloads, error codes, the stream's event order |
| `docs/openapi.json` | The machine-readable schema |
| `docs/frontend-integration.md` | How a web client is expected to use it (cookies, BFF, SSE) |

`routes.test.ts` reads that `openapi.json` directly and fails if a route the BFF
allows is missing from it, or if a request body the app sends uses a field the
schema does not have (the API answers unknown fields with 422). A backend change
that breaks the frontend therefore fails the tests in the same commit.

## What the BFF forwards

Only these requests reach the API. Anything else gets a 404 from the BFF. Path
ids must be UUIDs, and only the listed query parameters are passed on.

| Method and path (under `/api`) | Signed in | Notes |
|---|---|---|
| `POST /v1/auth/signup` | no | Always 202, whether or not the address can register |
| `POST /v1/auth/verify-email` | no | **Starts a session** (sets the cookie) |
| `POST /v1/auth/login` | no | **Starts a session**; 403 `email_not_verified` if unconfirmed |
| `POST /v1/auth/resend-code` | no | |
| `POST /v1/auth/password/forgot` | no | Always 202 |
| `POST /v1/auth/password/reset` | no | **Starts a session** |
| `POST /v1/auth/password/change` | yes | Signs out the user's other sessions |
| `POST /v1/auth/logout` | yes | **Ends the session** (clears the cookie) |
| `POST /v1/auth/sessions/revoke-others` | yes | |
| `GET /v1/me` | yes | |
| `PATCH /v1/me` | yes | Display name |
| `DELETE /v1/me` | yes | Needs the password; **ends the session** |
| `GET /v1/conversations` | yes | `limit`, `cursor`; newest activity first |
| `GET /v1/conversations/{id}` | yes | |
| `PATCH /v1/conversations/{id}` | yes | Rename |
| `DELETE /v1/conversations/{id}` | yes | |
| `GET /v1/conversations/{id}/messages` | yes | `limit`, `before`; oldest first |
| `POST /v1/chat/stream` | yes | `{conversationId?, message}`; server-sent events |
| `POST /v1/conversations/{id}/regenerate/stream` | yes | Server-sent events |
| `POST /v1/messages/{id}/cancel` | yes | Stop |
| `PUT /v1/messages/{id}/feedback` | yes | 👍/👎 |
| `DELETE /v1/messages/{id}/feedback` | yes | Clear the rating |

The allowlist is `apps/app/src/lib/api/routes.ts`; the proxy is
`apps/app/src/lib/server/proxy-core.ts`.

## What the BFF does with each request

- **Session.** The token lives only in an httpOnly, SameSite=Lax cookie:
  `__Host-aichat_session` over HTTPS, `aichat_session` on plain-HTTP localhost.
  When the API issues a session, the BFF sets the cookie and returns only
  `{user}` — the token never reaches the page. It sends the token upstream as
  `Authorization: Bearer`.
- **Cross-site requests.** Anything that changes state must come from this app:
  `Origin` must match the app's own origin (or, with no `Origin`,
  `Sec-Fetch-Site: same-origin`). Otherwise 403 `forbidden`.
- **Bodies.** JSON only (415 otherwise), at most 64 KB (413).
- **Headers sent upstream.** `Authorization`, a fresh `X-Request-ID`, the
  `User-Agent`, and `X-Forwarded-For` taken from Cloudflare's `cf-connecting-ip`
  only. A client-supplied `X-Forwarded-For` is never passed on: the API trusts
  the first entry for its sign-in rate limits. The browser's `Cookie` and
  `Origin` are never forwarded.
- **Signed out.** An API 401 clears the cookie — except `invalid_credentials`
  (a wrong password on login, change-password or delete-account), which must not
  sign the user out.
- **Errors.** API error envelopes pass through as `{error: {code, requestId,
  fields?}}`; the app shows its own wording for each code, never the API's
  message. An unreachable API is a 503, and an answer from it that cannot be
  used (not JSON, no envelope) a 502 — both with the code `service_unavailable`.
- **Streams.** Server-sent events are piped through unbuffered. If the browser
  goes away (Stop, closing the tab, reloading), the upstream request is aborted
  and the API marks the reply cancelled. JSON requests time out after 30 s;
  streams have no total timeout (the API owns LLM timeouts).
- Every response is `Cache-Control: no-store`.

## The stream, as the app reads it

`: open` → `event: meta` → `event: token` × n (with `: keepalive` comments) →
exactly one of `event: done` or `event: error`. The parser
(`apps/app/src/lib/api/sse.ts`) accepts LF, CRLF and CR line endings, multi-line
`data:`, UTF-8 split across chunks, and ignores unknown events and malformed
JSON.

- **Stop** posts `cancel`, then keeps reading until the API's `done` (status
  `cancelled`, with the text written so far), for at most 3 s.
- **A stream that ends with neither `done` nor `error`** is shown as interrupted,
  and the app re-reads the conversation (`GET …/messages`) to show what the API
  kept. It never sends the message again.

## Known gaps in the contract

These need a backend change. The app does not work around them by inventing
endpoints.

1. **Feedback is not returned with messages.** A 👍/👎 is saved, but after a
   reload the app cannot show it without one `GET /v1/messages/{id}/feedback` per
   message. Needed: `feedback` on each message in `GET …/messages`.
2. **No conversation search.** Sidebar search filters the chats already loaded.
   Needed, if server-side search is wanted: a `q` parameter on
   `GET /v1/conversations`.
